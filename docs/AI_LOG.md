## Лаб. 3 — SQL/DAO-запит агрегації за місяць

**Завдання.** Скласти оптимізований SQL/DAO-запит для агрегації витрат за поточний місяць із групуванням за категоріями
(`SUM(amount) GROUP BY category`).

**Результат** (`data/local/db/SqlQueries.kt`)
```sql
SELECT category, currency, SUM(amount) AS total, COUNT(*) AS count
FROM expenses
WHERE timestamp >= :from AND timestamp < :to
GROUP BY category, currency
ORDER BY category, currency
```
* Період напіввідкритий `[from, to)` — рівно початок наступного місяця не потрапляє у поточний.
* Групування ще й за `currency`: сума різних валют беззмістовна; зведення робить домен за курсом.
* Покривний індекс `(timestamp, category, currency, amount)` — запит виконується без звернення до таблиці.
* Суми — `INTEGER` у копійках: `SUM` точний, без похибок `REAL`.

**Перевірка.** `SqlQueriesTest` виконує **ті самі константи** на реальному SQLite (`sqlite-jdbc`): групування,
межі періоду, порожні вибірки, точність, порядок, а також `EXPLAIN QUERY PLAN` — перевіряється, що використано
`COVERING INDEX index_expenses_aggregation`, а для «останніх» і «історії категорії» немає `TEMP B-TREE`.

**Виправлено за результатами перевірки.** Перша версія історії була одним запитом
`WHERE (:category IS NULL OR category = :category)`: `OR` із параметром не дозволяє SQLite використати індекс.
Розділено на `HISTORY_ALL` і `HISTORY_BY_CATEGORY`; додано індекс `timestamp` для `ORDER BY timestamp DESC, id DESC LIMIT n`.

## Лаб. 5 — Точне планування сповіщення та відновлення після перезавантаження

**Завдання.** Код точного планування сповіщення з урахуванням відновлення розкладу після перезавантаження
(`RECEIVE_BOOT_COMPLETED`).

**Результат**
* `domain/notifications/NextReminderTime.kt` — найближчі 20:00 рахуються в «настінному» часі, а не «+24 год»:
  коректно у дні переходу на літній/зимовий час (доба 23/25 год), на межах місяця, 29 лютого, у зонах з пропущеним
  днем (Самоа 2011). Рівно о 20:00:00.000 наступне — завтрашнє (без дубля).
* `notifications/ReminderScheduler.kt` — `PeriodicWorkRequest(24h)` з `initialDelay` до найближчих 20:00.
* `notifications/BootReceiver.kt` + `ReminderBootPolicy`: перезавантаження/оновлення застосунку → *гарантувати*
  розклад (`KEEP`); зміна часу/часової зони → *перебудувати* (інакше затримка «до 20:00», пораховану за старим
  часом, зсунеться). WorkManager і сам відновлює задачі після перезавантаження — `BootReceiver` це друга лінія захисту
  та єдине місце, де обробляються TIME_SET/TIMEZONE_CHANGED.
* `NotificationHelper` — канал, сповіщення, `PendingIntent` з `expensetracker://add`; `navDeepLink` відкриває екран додавання
  і при холодному старті, і через `onNewIntent` (режим `singleTop`).

**Перевірка.** `NextReminderTimeTest` (14 кейсів, у т.ч. годинний перебір протягом 400 діб: затримка завжди
в межах (0; 25 год]), `ReminderBootPolicyTest`. Сам WorkManager/сповіщення на пристрої не запускались.

**Рішення й компроміси.** Точні `AlarmManager`-будильники відхилено: `SCHEDULE_EXACT_ALARM` із Android 14 за замовчуванням
не надається, а для нагадування «о 20:00 ± кілька хвилин» достатньо WorkManager. Це вказано в README.
Замість `ExistingPeriodicWorkPolicy.CANCEL_AND_REENQUEUE` (у назві enum-а не було певності для цієї версії WorkManager)
використано `cancelUniqueWork` + `KEEP` — API, що існують стабільно.
